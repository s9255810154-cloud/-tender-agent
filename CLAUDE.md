# Тендер-агент для клининговой компании — контекст проекта

Этот файл — сводка всего, что обсуждалось и было решено в долгой чат-сессии
claude.ai при разработке этого проекта, ДО переноса в Claude Code. Читай его
в начале работы с проектом — здесь принятые решения, известные грабли и
то, что уже проверено на реальных данных, а что нет.

## Что это за проект

Автономный агент для клининговой компании: находит тендеры (гос/коммерческие),
парсит ТЗ, считает сметы. См. `tender-agent-architecture.md` — исходный
архитектурный документ (8-шаговый пайплайн).

**Базовые принципы (не нарушать):**
- LLM не считает деньги — только извлекает/сопоставляет данные; арифметика —
  детерминированный код.
- Human-in-the-loop обязателен: численность персонала, накладные/маржа,
  финальное утверждение сметы — решает эксперт, не агент.
- Структурированный JSON-вывод от Claude на этапе извлечения ТЗ.

## Обязательный стандарт для всех Excel-смет

1. Порядок разделов сверху вниз: срок контракта → цена/мес → цена/год →
   численность персонала → расходные материалы → всё остальное.
2. Сопоставление расходных материалов с прайс-листами (`matcher.py`/`resolver.py`)
   запускать ВСЕГДА для каждой сметы — никогда не оставлять заглушку.
3. Количество материалов в таблице — ФОРМУЛА (норматив × база), не
   зафиксированное число, чтобы эксперт мог скорректировать вручную.
4. Таблица материалов всегда показывает наименование поставщика.
5. Новые сметы писать через `smeta_builder.py` (общий модуль, см. ниже), а не
   копировать код из старых `*_smeta_export.py`.

## Общий модуль smeta_builder.py

Систематизирован 2026-09-29 — вынес повторяющийся код из 10+ скриптов смет в
общий модуль: стилевые константы, класс `SmetaSheet` (курсор строки, не нужно
отслеживать номера строк вручную — источник минимум 2 реальных багов раньше),
`build_contract_term_section()`, `build_price_summary_section()`,
`build_materials_table()` — последний реализует весь стандарт выше
автоматически, включая НАСТОЯЩИЕ Excel-формулы для количества материалов
(норматив×площадь×дни×коэффициент, все базовые величины — editable-ячейки).
Проверено на миграции `mlrz_smeta_export.py` → `mlrz_smeta_export_v2.py`:
recalc — 0 ошибок, все суммы совпали до копейки с оригиналом.
Специфичные для объекта секции (аренда техники, твёрдый пол/скидка,
лето/зима) по-прежнему пишутся в скрипте объекта через `SmetaSheet`.

## Критический повторяющийся баг — "area-trap"

В разделе ТЗ "Перечень объектов закупки" объём указан как НАКОПЛЕННЫЙ за весь
срок контракта (площадь × число обработок), а НЕ площадь объекта. Реальная
площадь — в отдельном приложении ("Перечень помещений" для помещений,
"Перечень территорий..." для территорий). Встречалось минимум 3 раза на
разных типах документов. Для помещений накопленный объём восстанавливается
через GCD месячных объёмов (`compute_real_area()` в `tz_extraction.py`); для
территорий — тем же принципом, но НЕ единым пулом (разные строки = разные
физические зоны), нужен outlier-tolerant поиск (`find_best_area_candidate()`).

Другой пример этого же класса багов: порядок проверки типа документа в
`detect_document_type()` / `tz_document_templates.json` — специфичные
(гибридные) типы должны идти ПЕРЕД общими, иначе общий тип "ворует"
классификацию. Этот класс багов (specific-before-general ordering) повторялся
минимум 3 раза в разных местах кода — системная закономерность, проверять
при добавлении новых типов/правил.

## Что проверено на реальных данных (не просто смоделировано)

- **ФОТ/зарплаты**: модель сошлась с реальным табелем МЛРЗ с расхождением
  0,11% — считается решённой задачей.
- **Материалы для помещений/промышленных объектов**: калибровано по
  независимым реальным данным (Краун — ₽/м², МЛРЗ — сверка с тем же
  диапазоном). Крупные объекты с механизированной уборкой требуют отдельной
  нормы (дозирующие системы разбавляют концентрат 1:100-1:400, а не
  ручное мытьё 5мл/м²) — см. `моющее_средство_полы_механизированная_уборка`
  в `consumable_norms.json` + общий коэффициент ×1/7 для прочей химии
  на крупных объектах (из ОДНОЙ точки калибровки, не проверено по каждой
  категории отдельно).
- **Расценки по территориям (ГЭСН/СН-2012)**: три независимых реальных
  объекта в базе — ГЦПиКР, Лужники, ГБУЗ «Центр крови им. Гаврилова»
  (`real_territory_smeta_gbuz_gavrilov.json`). Прямое сравнение rate_per_unit
  по одинаковым шифрам между контрактами показало расхождения 2-5x — это
  НЕ обязательно ошибка (ГЭСН-ставки зависят от объёма/коэффициентов), но
  точка, которую стоит исследовать глубже при наличии ещё объектов.
- **Норматив численности** (`staff_norms.json`): используется пользовательский
  800-1200 м²/чел (норматив Роструда 370,4 м²/чел ПО ПРЯМОМУ УКАЗАНИЮ
  пользователя удалён из базы). НЕ применим к объектам с периодической
  (не ежедневной) моделью уборки или крупным промышленным цехам —
  см. `_scope_warning` в `staff_norms.json`.

## Прайс-листы расходных материалов

- `data/general_opt_price.xlsx` — 4093 позиции, поставщик "ТК Сервис"
  (оптовый прайс).
- `data/tk_service_manual_additions.json` — 17 позиций, добавленных вручную
  из реальных счетов (проверено: 36 из 38 SKU по двум реальным счетам уже
  были в базе — добавлены только 2 действительно отсутствующих).
- `data/retail_suppliers_manual_additions.json` — 35 позиций с розничных
  сайтов (almin.ru, proff-comfort.ru; lider-gk24.ru не до конца проверен —
  PDF-прайс извлёкся частично), скидка 28% (пользователь подтвердил этот
  процент как реальный для своей компании). ВАЖНО: сопоставление
  "уже есть / отсутствует" делалось по эвристике совпадения ключевых слов
  в названии — не 100% гарантия, при использовании в смете `resolver.py`
  всё равно перепроверяет каждую позицию.
- Загрузка всех источников — через функции в `price_parser.py`
  (`load_general_opt_price_list`, `load_tk_service_manual_additions`,
  `load_retail_suppliers_manual_additions`, `load_almin_price_list`,
  `load_vse_instrumenti_price_list`).

## Единица измерения упаковок — критический баг, уже исправленный

`estimate_purchase_quantity()` в `unit_price.py` ВСЕГДА использовать для
перевода "сырой потребности" (например, литров в месяц) в количество
УПАКОВОК к заказу перед умножением на цену за упаковку. Раньше прямое
умножение литров на цену 5-литровой бутылки завышало стоимость материалов
в ~3 раза — баг найден и исправлен, но при написании нового кода для
материалов эта функция обязательна, не писать расчёт "в лоб".

## Не проверено / не начато

- **`extract_tz_structured()`** (`tz_extraction.py`) — реальный вызов
  Anthropic API НИ РАЗУ не тестировался вживую (в чат-песочнице не было
  прямого доступа к api.anthropic.com). Первое, что нужно проверить на
  сервере после установки `ANTHROPIC_API_KEY`.
- **Step 1-2 архитектуры** (сбор тендеров) — не подключено ни к одному
  живому источнику. Разобрались с двумя каналами: ЕИС zakupki.gov.ru —
  бесплатный SOAP-канал (`int44.zakupki.gov.ru/eis-integration/services/getDocsIP`),
  но скудная документация и строгий формат XML-запросов; Контур.Закупки —
  платный (от 26-43 тыс ₽), без публичной документации по эндпоинтам,
  подключение только через отдел продаж. ЕИС — более реалистичный кандидат.
- **Территория/озеленение** — модель материалов один раз занизила смету на
  ~31% (объект Звезда/Главкино) — открытый пробел, не закрыт.
- Тестов (pytest) нет — только demo-скрипты, проверенные вручную на реальных
  документах из переписки.
